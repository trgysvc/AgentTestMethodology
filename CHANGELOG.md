## Version 10 — 2026-09-09

**First live k=5 certified run of the 126-block dataset (`run_qwen3.5-9b-4bit_20260908_k5_autorun1732`) — published together with the dataset itself for the first time, plus 3 new agent bugs found in the process.**

- **The 126-block dataset (`datasets/golden_dataset_126.json`) is published for the first time this version** — Version 9 (2026-09-05) had grown it from 94 to 126 blocks (closing every UBID coverage gap found in that day's audit) but explicitly deferred both the first live battery run and the sanitization/publish pass. Both are done now.
- **Run duration: 21.8 hours** (79,851s), fully unattended (`nohup`+`disown`+`caffeinate -s`, survived the operator's session closing). Preceded by 3 rounds of same-day agent fixes (see the private source repo's DEVLOG, `[2026-09-08]` entries): a `handleExecution` completion-claim verification bypass ("CRITIC SKIP"), a `system_sleep` tool that previously ignored its own delay parameter, a `.chatting`-mode false-completion-claim gap, a `/api/agent` CLARIFY-answer context-loss bug, and a new systemic CategoryMapper reachability test that itself found and fixed 3 more previously-unknown tool-visibility gaps (`contacts_find`, `apple_accessibility`, `skill_patch`).
- **Headline numbers, reported honestly at two layers (not one blended figure):**
  - Raw: **63/126 pass@1 (50.0%)**, 47 graded / 79 needs_review.
  - Trial-level (578 total trials): 17.6% pre-task hardware-gate declines (this test machine ran the model, `xcodebuild`, and `swift test` concurrently for the entire 21.8h), 2.2% deliberately-skipped manual-approval-gated blocks (unattended-run design, not a failure), 1.9% confirmation-collision, 1.0% request-timeout, 3.5% other known infra gaps (JUDGE blocks pending real Cohen's kappa calibration; a couple of `STATE` blocks with no gradable `expected` field set).
  - **Excluding all of the above (452 genuinely-attempted trials): 69.9% real pass rate** — a meaningfully cleaner signal than the raw 50.0%, and higher than the prior 94-block run's contamination-adjusted rate, though the two runs' environments (interfering apps open vs. closed) were not held constant enough to attribute the difference to any single cause.
- **A specific operational safety precaution, disclosed:** `EK-TOOL-51` tests a deferred `system_sleep` call ("set a timer that puts the computer to sleep in 1 minute, not immediately"). The same-day fix made the tool's delay parameter functional for the first time — previously it either slept immediately regardless of params, or the model picked the wrong tool, so a real deferred trigger had never been observed. Running this block mid-battery, unattended, risked a real sleep event corrupting every subsequent block. A content-identical copy of the dataset (verified via a full diff — only block order changed) moved `EK-TOOL-51` to the very last position; the harness's block-then-trial loop structure means all of its own 5 trials run consecutively at the very end, so even a real trigger there could not have affected anything before it. **Confirmed after the run: the model chose `set_timer` over `system_sleep` in all 3 real trials, and the machine's `uptime` was unbroken since before the run started — it never actually slept.**
- **3 new, previously-undiscovered agent bugs found via detailed audit-log review after the run** (not visible in the automated grader's per-trial reason strings alone). Each was investigated and a fix attempted the same day, then **re-tested live against the exact same scenario before publication** — reported below exactly as verified, not rounded up:
  1. **`ContactsTool` (`contacts_find`, UBID 38) was completely broken by an AppleScript syntax error — fixed, fully verified. ✅** Its script used `person` as a `repeat` loop variable name, which collides with the reserved `person` class name in Contacts.app's own AppleScript dictionary (`"128:134: syntax error: Expected variable name or property but found class name"`). Every real invocation failed. This tool had simply never been reachable in FOCUSED MODE before this run's own CategoryMapper fix — the bug is old, only the visibility that exposed it is new. **Live-verified:** the loop variable was renamed and the exact failing query re-run directly (`osascript`), returning 24 real contacts with no error.
  2. **The `EVIDENCE GUARD`'s completion-claim keyword list was narrower than the natural language it needs to catch — the fix worked exactly as intended, but exposed a second, deeper, still-open flaw in the same guard. ⚠️ Partially verified.** In the `EK-TOOL-51` trials above, after calling `set_timer`, the model wrote "Zamanlayıcı başarıyla kuruldu ve 1 dakika sonra bilgisayar uyku moduna girecek" ("the computer will go to sleep in 1 minute") — a claim the tool result never supports. The guard's trigger-keyword list didn't include "kuruldu" (was set up) or "girecek" (will enter/go into). The list was broadened and **re-tested live**: the broadened trigger correctly fired on the identical claim this time — but the guard's separate evidence-check then matched the word "started" in the tool's own output ("Timer started for 600 seconds") as sufficient evidence, because **the guard only checks whether the last tool observation contains any generic success keyword, never whether that keyword's evidence actually supports the specific claim made.** "Timer started" is real evidence a timer started, not that the computer will sleep — the same false claim still reaches the user today, for a different, deeper reason than this fix addressed. Deliberately NOT patched further: removing "started" from the evidence-keyword list risks breaking other legitimate scenarios (e.g. "did the git clone start?") without a real claim-to-evidence matching mechanism to replace it — tracked as an open architectural item, not a one-line fix.
  3. **Systematic tool-selection confusion between `set_timer` and `system_sleep` — fix applied, not yet confirmed. ❌ n=1 negative.** The Turkish prompt phrasing "bir zamanlayıcı kur" ("set up a timer") lexically matches `set_timer`'s own name far more directly than `system_sleep`'s, and the model picked the lexically-closer, functionally-wrong tool in 3/3 real trials in this run. An explicit cross-reference was added to both tools' descriptions and **re-tested live**: the model chose `set_timer` again, unchanged. One live trial does not confirm or disprove the fix — left open pending further samples.
  - **Net result: a real deferred-sleep trigger has now been observed zero times across every live test to date, including this same-day re-test — a fourth consecutive negative.** The delay mechanism itself is verified correct (code-level); the model has simply never yet been observed choosing the right tool for this phrasing.
- **A confound flagged, not fully explained:** `ScreenCaptureKit`/TCC screen-recording permission errors ("the user declined") appeared 12 times across the run, affecting `semantic_vision` and `visual_audit` calls — but intermittently, not consistently (some vision-tool calls in the same run succeeded). This may have depressed the Vision-tier results independently of the semantic_vision 24GB hardware gate; the cause was not conclusively identified and is left as an open item rather than asserted.
- **A qualified positive signal — mechanically confirmed, but neither block scored a pass.** The `apple_accessibility` and `contacts_find` CategoryMapper fixes from earlier the same day were both directly observed firing in this run, something structurally impossible before it: `EK-TOOL-53` called `apple_accessibility` in 2 of its 3 real trials, and `EK-TOOL-56` called `contacts_find` in 1 of its 3 real trials (which is how bug #1 above was discovered at all). Neither block produced an actual pass, though, for reasons distinct from reachability itself: `EK-TOOL-53`'s two successful invocations were graded `fail` as "double dispatch" (the model also called `learn_application_ui` first, and the grader's exactly-one-tool rule doesn't allow that), and its third real trial never called the tool at all; `EK-TOOL-56`'s other two real trials never called `contacts_find` either (the model used memory recall instead, non-deterministically). The reachability mechanism is proven correct — the tool is reachable and does get called — but "reachable and called" is not the same claim as "block passes."
- Per this document's established practice, no historical run's figures were altered — this is a new, separately-dated entry.
